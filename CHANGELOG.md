# Changelog

All notable OTRI releases and material methodology changes will be documented here.

## Unreleased

- **Race calendar.** The races page has a Calendar view (`#races?view=calendar`, filters kept in the address so a filtered calendar is a shareable link): upcoming events by month with a countdown, one row per event with its distances, courses on OTRI highlighted for a target time before race day. Every event and every upcoming race page has "Add to calendar" (`.ics` and Google); `GET /calendar.ics` is a subscribable feed (`webcal://`, optional `?country=`). Runners can **suggest a race** from the calendar (facts only); it reaches the admins as a report carrying the facts, and Admin → Reports → Create listing puts it on the calendar in one step after a check against the race's website. The view switch and the suggestion form are there even when no race is public yet.
- **Demo races are not public by default.** `scripts/seed_demo_data.py` (run on every deploy) creates the synthetic demo races unpublished and leaves the publish state of existing ones alone; `--publish` shows them all (local and staging sites), `--unpublish` hides them all. Admins still see them under Admin → Events & races and can publish one by hand. The home page's races section appears only when there is a scored race to show, and says "Demonstration races" only when that is all there is.
- **Course permission on unclaimed listings is optional.** A course file can be attached to a race nobody owns without a permission note (single and bulk upload). A note is still recorded when given, and only then does the public page say the course is shown with permission; otherwise it says "course file". The policy in `DATA_POLICY.md` is unchanged in substance: the uploader answers for the right to publish the file.
- **Uploaded course files are sanitized before they are stored.** Every path that keeps a GPX (a race's course, single or bulk upload, and a shared calculator course) now stores and serves positions and elevations only: no author, device, timestamps, heart rate or other extensions, waypoints or notes (`course/sanitize.py`). Coordinates round-trip exactly, so the stored file measures bit-identically to the upload (tested on every fixture). What the file said about its origin (creator, author, copyright holder, licence, links) moves to the race's private record next to `raw_sha256`, and is not returned by the public measurement endpoint; the permission rules for course files are unchanged. `scripts/sanitize_stored_gpx.py` (dry run by default, `--apply` to rewrite) cleans files stored before this change.
- **Bulk course upload for admins.** The Listings box on the admin page takes many GPX files at once, matches each to a race without a course by its file name (a guess the admin can change), and attaches them one at a time with one shared permission note or a note per file. Unclaimed races are still refused without a recorded permission.
- **Race listings** ([`docs/product/race-listings.md`](docs/product/race-listings.md)). A race can be shown on the races page before anyone has uploaded results: admins add unowned listings from race facts (one at a time or by CSV), and organizers can list their own upcoming race. A listing page shows the facts, the course when OTRI may show it, an "I'd like scores" button with a public count (one per visitor, no personal data stored), a message the runner can send to the organizer, and "I organize this race", which files a claim in the admin reports queue; an admin then assigns the event to the organizer's account. Results stay behind publishing. A course file on an unclaimed listing is refused without a recorded licence or permission, in line with the rule against copying GPX files from the web. The races page gains a status filter, UPCOMING / AWAITING RESULTS badges and a default order that keeps scored races first; the admin page gains CSV import, a most-asked-for table, list/unlist and assign.
- **Vertical races, and a new build id `0.9.0-course-standard-domain-gated`** ([OEP-002](docs/governance/oep/OEP-002-domain-gating-and-vertical-races.md); still OTRI model 0.1.0, every existing score unchanged). The steep-terrain term was calibrated on mountain courses with up to a quarter of their distance at 20 % or steeper; on an uphill-only course it multiplies demand by 1.6, so a 50-minute vertical kilometre scored 1000. A course with a steep share above 0.50 (or, from official figures alone, an average grade of 20 % or more) is now **listed with finish times and no score**, with the reason on the leaderboard, the organizer's pre-flight check and the calculator, and it adds nothing to a runner index. Confidence also drops to `Low`, with the reason, when more than a fifth of a course's demand comes from ground beyond the ±45 % gradient domain, and below 1.5 flat-km. Race summaries carry `is_vertical` and `elevation_loss_m`; the races page shows a VERTICAL badge and has a Vertical filter. Official figures averaging beyond 45 % are clamped and flagged instead of being unscorable. Races stored under `0.8.0-course-standard-power` replay unchanged.
- **Transactional emails redesigned.** Verification, password reset, sign-in code and admin report emails share one layout: heading, one or two plain sentences, a button plus the same link in text, how long it is valid, what to do if you did not ask for it, and a footer that says why you received it. Each message carries a plain-text alternative and a reply-to of hello@otri.run; subjects are "Verify your email address for OTRI", "Reset your OTRI password", "<code> is your OTRI sign-in code".
- **FAQ.** A searchable FAQ page on the public site (`#faq`, linked from the navigation and footers; `#faq?q=…` deep-links a search) with plain answers about scores, courses and GPX files, the runner index, publishing a race and the project. Older scoring builds are labelled by their build id rather than as "superseded"; the demo seed keeps GPX-less demo races on the model in production so public demo leaderboards never show a retired build.
- **Scale and operations.** A GitHub Actions workflow runs the Python suite against Postgres on every pull request and push (`tests.yml`; add it as a required check). The API uses a per-process connection pool instead of one Postgres connection per request, and the hot lookups (results by race, races by event and by publication, events by organizer) are indexed. Anonymous public reads carry `Cache-Control: public, max-age=30` and nginx microcaches them (re-run `03-configure-nginx.sh`); anything personal stays `no-store`. Optional browser error reporting to Sentry when the site is built with the `VITE_SENTRY_DSN` repository variable. Every screen sets its own tab title, and the three apps carry Open Graph tags with a preview image for shared links. The admin overview lists the installed terrain tiles, with a runbook for adding regions in `scripts/deploy/README.md`.
- **Methodology folder consolidated.** `docs/methodology/0.1.0/OTRI-MODEL-0.1.0.md` is now the complete, self-contained specification of the production model: course demand, terrain adjustment, the human ceiling with its held-out validation, the curve, confidence, every constant with its origin, the worked example, the required tests and the limits. The eight development-build papers under `docs/methodology/v0.1/` … `v0.8/` were removed (they remain in git history and every build id still runs); code comments, the calculator's methodology note and the docs index point at the one page. Older entries below still name the removed paths.
- **API attack surface.** GPX parsing goes through defusedxml (entity bombs and external entities are a 422, not a hang or a file read); results files are capped at 50,000 rows and non-spreadsheet zips are a clean 422; bodies over 20 MB are refused before being read; every response carries nosniff, X-Frame-Options DENY and a referrer policy, and anything personal is `Cache-Control: no-store`; `/gpx/analyze` is rate-limited (60/min per IP); GPX parsing, results validation and scoring run off the event loop; runner search escapes LIKE wildcards; every text input has a length limit; upload temp files only ever get a plain extension; the events list makes one query for race counts instead of one per event. nginx config gains HSTS, the same headers and a per-IP request budget (re-run `03-configure-nginx.sh`). `tests/unit/test_api_security.py` checks every route's auth requirement from the app's own route table, ownership, forged tokens, injection strings, traversal, parser bombs, mass assignment, enumeration and headers.
- **Calculator slider** spans each course's own range, from the human-best time (score 1000) to a slow finish (score 200), instead of a fixed 10 minutes to 24 hours; typed times still go anywhere up to 200 hours.
- **Organizer sessions moved into an HttpOnly cookie.** The web app no longer stores the token in the browser's storage, so a cross-site-scripting bug could not exfiltrate a session; the cookie is SameSite=Lax and Secure behind HTTPS, state-changing requests need the app's `X-OTRI-Client` header (CSRF guard), and `POST /auth/logout` ends the session on that device. Bearer tokens keep working for API clients, scripts and earlier sign-ins.
- **Production hardening.** Sessions carry a per-account version and are revoked by password change, turning 2FA off, "Sign out everywhere" and account deletion; rate limits moved to the database (shared by all workers, survive restarts) with a per-account lockout after ten wrong passwords; numbered one-shot schema migrations (`api/migrations.py`, `scripts/migrate.py`) on top of the idempotent baseline; every email send logged with its Resend id (`/admin/emails`, counts on the admin overview); `/health` for the watchdog and uptime checks; optional Sentry via `SENTRY_DSN`; self-service data export and account deletion on the account page; shared-course eviction serialized so concurrent uploads cannot exceed the budget. Droplet scripts: backups now integrity-checked, include shared courses and `.env`, keep 30 days and copy off-site with rclone when configured; a restore script with a scratch-database test mode; a systemd watchdog timer (auto-restart, disk and service alerts by email); a sudoers file that limits the deploy user to the commands the scripts need; the deploy script keeps optional `.env` settings across redeploys. The organizer profile no longer asks for a phone number.
- **Calculator:** a "What is a GPX, and where do I get one?" note under the course step, with the full guide in `docs/WHAT-IS-A-GPX.md`.

- **The production scoring model is now named `OTRI model 0.1.0`** everywhere users see it (`docs/methodology/OTRI-MODEL-0.1.0.md`). It consolidates the development builds V0.1–V0.8 into one specification; no formula, constant or stored score changes. The API keeps returning the build id `0.8.0-course-standard-power` as `scoring_version` so every stored score replays exactly; the site maps that id to the public name and shows any older build id as a superseded build. Public model names change (`0.2.0`, …) only when scores can change.
- **Organizer accounts: sign-in security and profile.** Remember me (30-day session, ticked by default) or a 12-hour session; two-factor authentication with an authenticator app (TOTP) or emailed codes, with ten one-time recovery codes; a password policy at sign-up and reset (10–128 characters, no common passwords, not built from the email) with a strength meter; an account page for profile details (name, organization, website, country, phone, bio), password change and two-factor settings; organization and website appear on the organizer's public race pages. Sign-up now requires accepting `TERMS.md` and `PRIVACY.md` and records when; an optional, revocable newsletter consent is stored with its timestamp and exported for admins as `/admin/newsletter.csv`.
- **Every page ends with the build banner** (commit, age, API restart time); the three HTML shells show an animated OTRI mark while the app loads; unknown routes, missing races and missing runners get proper not-found pages, GitHub Pages gets `404.html`, and a render error shows a recovery page instead of a blank screen.

- **New default scoring model `0.8.0-course-standard-power`** (`docs/methodology/v0.8/OTRI-POWER-CURVE.md`). One power law for the whole scale, `score = 1000 × f^0.85` with `f` the runner's fraction of the human-ceiling rate; the last V0.1 demo anchors (349, 544) retire. V0.6/V0.7 were already `1000 × f^0.692` above 544, a concave shape that flattered the middle of the field (53% of the ceiling scored 643). The top holds — world bests 957–1000, the 100-mile mountain winner 958 — and every score below drops, more so further down: a runner at 53% goes 643 → 581, a last finisher at 22% goes 371 → 274. 0.85 is a stated judgement, not a fit and not a reference to any third-party index. V0.7 and earlier remain selectable and reproducible.
- **`course-measurement-v3`: geodesics and smoothing in C/numpy.** Same formulas, windows and thresholds as v2; `pyproj.Geod` replaces the pure-Python `geographiclib` solves and the smoother runs in numpy. Agreement with v2 on three real courses, end to end: distance within 1.4e-8 m, gain/loss within 5.5e-9 m, every profile point within 2.3e-8 m, flags and scores identical (the reference 100-miler 966, CM6 707, Phuket 554) — but profile hashes differ, hence the version bump. Measured live after deploy: the reference 100-miler end to end 7.9 s → 4.4 s cold (2.3 s cached; 61.6 s before the sampler and cache work), score unchanged at 987 on the DEM; measure step 0.51 → 0.12 s locally. The first request each worker serves after a restart also pays the one-time tile checksum (~1.5 s). Stored v2 measurements replay unchanged. `pyproj` is now a runtime dependency.
- **DEM measurement ~8-35x faster, and cached.** Profiling on the production droplet (1 CPU, 1 GB) showed `RasterProvider.sample()` re-hashing every tile on each call and issuing one windowed GDAL read per bilinear neighbour per 10 m grid point. Tiles are now checksummed and opened once per process, and sampling is vectorised in numpy (one bounding-window read per tile per course); the result is bit-identical to the scalar implementation, which is kept as a test reference. The API also caches each measurement on disk (`data/cache/measurements/`, keyed by file hash + terrain manifest, bounded), so the prototype's repeated analyses of the same course re-score without re-measuring. Measured live: Reference 100-miler, 171 km 61.6 s → 7.9 s cold / 2.3 s cached; Phuket 14.6 km 9.8 s → 0.28 s / 0.03 s; scores and profile hashes unchanged.
- **New default scoring model `0.7.0-course-standard-dem-gated`** and **`course-measurement-v2`** (`docs/methodology/v0.7/OTRI-DEM-GATED-MEASUREMENT.md`). The curve is V0.6's, unchanged; what changes is what a score is allowed to claim. Under V0.6 the same route recorded by two devices measured up to 25% apart and the score said nothing. Measurement v2 records the track's median point spacing and marks anything sparser than 30 m `needs_review` (such tracks chord the switchbacks and measure the course short; at or under 30 m the error stays within ~2–3% on four real courses). When a pinned Copernicus GLO-30 manifest is configured (`scripts/deploy/06-install-dem.sh`), elevation comes from it instead of the uploaded file; a course the tiles do not cover falls back to uploaded elevations *announced*, never silently. Every V0.7 score now carries a confidence label — `High` only with DEM elevation on a dense track, otherwise `Low` with the reason in `quality_flags` — shown in the prototype. V0.6 and all earlier models, and stored v1 measurements, remain selectable and reproducible. Confidence gates on route reproducibility only (sparse or disconnected geometry, or implausible *uploaded* elevation when the upload is the source); the scoring-domain grade flag still marks a measurement for review but no longer blocks `High`, and uploaded-point noise is not held against a DEM-sourced measurement. DEM-sourced production scores differ a few % from the uploaded-elevation pins in the V0.5/V0.6 notes on alpine courses (the reference 100-miler 987 vs 966) — documented, not re-tuned.
- **New scoring model `0.6.0-course-standard-smoothed-upper`** (`docs/methodology/v0.6/OTRI-SMOOTHED-UPPER-CURVE.md`). V0.5 unchanged except that V0.1's 692 demo anchor is dropped, so a single power law runs from the 544 anchor to the world-best 1000 anchor. The 544→692 segment was ~45% more elastic than its neighbours, an artefact of fitting through three demo finishers, and it amplified every uniform course-level correction in the 550–700 band — V0.5 lifted the reference race's 2:40 finisher by 63 points but its winner by only 50. V0.6 halves that mid-pack lift, leaves every score at or below 544 identical to V0.5, and keeps the mountain-ultra winner at 966. Because the curve is universal, road runners who sat in the same inflated band come down too (a 1:45 half: 700 → 667). V0.5 and all earlier models remain selectable and reproducible.
- **New scoring model `0.5.0-course-standard-terrain-adjusted`** (`docs/methodology/v0.5/OTRI-TERRAIN-ADJUSTED-DEMAND.md`). Keeps V0.4's score curve and instead adjusts **course demand** for what the Minetti gradient-cost integral does not price: that polynomial was measured on a treadmill, so it understates sustained steep mountain terrain and ignores altitude entirely. Both are now measured from the course GPX — the share of distance at or above 20% grade, and distance-weighted elevation above 1500 m — and applied as a terrain factor on demand. Road courses have a factor of exactly 1.000 and are untouched; an elite mountain 100-mile performance moves from 889 to 970. Two consequences to note: the steepness term cannot distinguish technical footing from plain steepness (GPX does not contain it), so it lifts all steep courses together, and V0.1's demo/test anchors therefore shift under this model (the reference race's 2:20:30 moves from 692 to 737). `STEEP_COEFFICIENT` is calibrated to a single real performance — see the methodology note's limitations before treating it as measured. V0.4 and all earlier models remain selectable and reproducible.
- **New scoring model `0.4.0-course-standard-endurance-referenced`** (`docs/methodology/v0.4/OTRI-ENDURANCE-REFERENCED-CURVE.md`). A score now measures what fraction of the best humanly-possible performance on a course of that demand the runner achieved, so race length no longer moves the score: the same-calibre run scores the same at 5 demand-km and at 700, and 1000 means world-best at every course size. This fixes two defects at once — V0.3's Riegel `b=1.06` correction was derived from sub-4-hour road racing and under-corrected badly beyond it (a real 100-mile mountain-race winner scored 783), while V0.1's 1000-anchor was an acknowledged extrapolation that saturated the short end (a 15:06 5 km also scored 1000). V0.1's three real score anchors (349/544/692) are unchanged; only the invented 1000-anchor and the course-size scaling are replaced. The short segment of the new reference curve independently reproduces Riegel's published `b=1.06` to three decimals over the range his data covered. `0.3.0-course-standard-duration-scaled` and all earlier models remain selectable and reproducible.

- Recalibrated the Course Standard model's default scale anchors (`1.1.0-course-standard`: 500 points at 3.5 demand-km/h, 1000 points at 10.5 demand-km/h) after real-world testing showed the spec's own literal anchors (15.0/22.5 demand-km/h) implied absurdly fast absolute finish times (~70 minutes for 500 points) regardless of course length, clustering realistic multi-hour trail finishes at 0. The spec-literal curve remains selectable as `1.0.0-course-standard` for spec-fidelity comparisons.
